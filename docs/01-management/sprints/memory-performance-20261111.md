# 메모리·성능 최적화 Sprint

- 방법론: Sprint Delivery. 사용자 요청의 구현·Docker 반영·커밋·푸시·develop 병합을 수행한다.
- 범위: 현재 프로젝트만 수정. 기존 79개 미커밋 파일은 보존하며 변경을 섞어 커밋하지 않는다.
- 제외: DB·스키마·계정·볼륨 이관, AI 모델·문맥·추론 정책 변경, 다른 서비스/operations 파일 변경, CI/CD.

## 1. 같은 조건의 측정

### 1.1 운영 상태와 합성 기준선

현재 컨테이너/이미지/연결/메모리를 읽고 작업 전 파일 SHA256을 저장한다. 별도 tmpfs PostgreSQL·합성 기사 300건으로 동일 이미지/CPU/768MiB 한도에서 기준/개선/개선/기준 순으로 비교한다. 실제 RSS/PSS/cgroup과 p95·처리량·오류·유휴 연결을 측정한다. 운영 계정이나 DB를 부하 시험에 사용하지 않는다.

### 1.2 수용 기준

실제 메모리 감소, 오류 0, 동일 시험의 p95/처리량 악화 20% 이내를 목표로 한다. 잡음이 크면 재측정하고 실패를 PASS로 바꾸지 않는다. 컨테이너 한도 축소를 메모리 절감으로 보고하지 않는다.

## 2. 제한된 실행 자원

### 2.1 JVM·연결 풀·HTTP 스레드

Java25 작은 객체 헤더, 역할별 힙·코드 캐시, 유휴 DB 연결과 HTTP 스레드를 조정한다. 운영자 override를 유지한다. 중첩 트랜잭션과 worker 스케줄러에 필요한 연결 여유를 확보한다. Docker·Compose·Helm에서 같은 이미지 실행 정책을 사용한다. AI는 고정 모델·native binary·context를 유지하고 5분간 유휴하면 메모리만 해제한다. 각 모델의 두 번 sleep/wake, 동일 합성 출력, health200·인증401·재시작0을 검증하고 cold-wake 비용을 기록한다.

### 2.2 회귀와 공급망

실제 launcher 시험, 기존 단위/통합/E2E, 인증·quota·캐시·숨김·메일·worker 정지/재시작, JAR/SBOM/이미지 검사를 수행한다. 14개 AI 클래스 바이트 지문이 같아야 하며 미확인 결과를 변경하지 않는다.

## 3. 납품

### 3.1 프로젝트 서비스만 교체

기존 공통 운영 flock을 보유하고 컨테이너 설정을 다시 확인한다. 이전 이미지·설정을 보존하고 web/worker는 같은 앱 이미지, translator/classifier는 같은 AI 이미지로 교체한다. 기존 네트워크/볼륨/secret/포트와 proxy·DB·다른 서비스는 보존한다. 실패하면 이전 실행 구성으로 복원한다.

### 3.2 검토와 병합

검증된 계약·사람 wrapper로 커밋/푸시/PR, 독립 read-only 코드 리뷰와 App current-head 승인 후 develop 병합한다. 정확한 병합 브랜치의 원격·추적·로컬 ref를 정리하고 기존 미커밋 파일의 내용을 비교한다. 결과는 검증서와 진행 상태에 기록한다.
